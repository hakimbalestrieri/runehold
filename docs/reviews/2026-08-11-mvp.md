# Runehold MVP Code Review — 2026-08-11

## Context

Review scope: the complete local MVP described by `docs/specs/runehold-mvp.md`,
including the XP economy, village transactions, profile persistence, Swing panel,
and RuneLite lifecycle integration.

## Findings resolved

### Required: serialize domain mutations

The first UI implementation upgraded buildings directly on Swing's event dispatch
thread while XP events mutated the same `VillageState` on RuneLite's client thread.
The panel now emits an upgrade request. `RuneholdPlugin` queues that command through
`ClientThread`, and the EDT receives an immutable `RuneholdViewModel` for rendering.

Regression coverage verifies that clicking a panel button emits a request without
mutating the domain on the EDT.

### Required: prevent queued double upgrades

An enabled Swing button could emit two commands before the first refresh. The
button now disables itself immediately after activation. A regression test performs
two clicks and verifies that only one command is emitted.

### Required: bound untrusted persisted state

Profile JSON is a local but untrusted boundary. The codec now rejects payloads over
64 KiB before parsing, limits XP tracking maps to 64 entries, validates balances,
dates, remainders, schema version, building names, levels, and unlock progression,
and falls back to a fresh state on any invalid input.

## Five-axis review

- Correctness: deterministic rules and failure paths are covered; upgrades are
  atomic; profile changes establish fresh baselines; daily progress rolls on load.
- Readability: business rules live in the domain, catalog values have one source,
  and RuneLite orchestration remains in `RuneholdPlugin`.
- Architecture: the domain has no RuneLite/Swing imports; UI consumes domain
  previews; persistence owns JSON validation; mutable commands use one thread.
- Security: no network, telemetry, authentication, secrets, game input, dynamic
  code, reflection, native access, external processes, or Java serialization.
- Performance: each stat event is constant-time map work; the UI renders four rows;
  no tick/frame polling or blocking I/O exists.
